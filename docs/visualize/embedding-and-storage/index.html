Embeddings and Vector Storage, Visualized in 3D

Every chunk becomes a list of numbers, and those numbers become a position. Similar chunks land close together, and the index links neighbours so search doesn't have to check everything.

Approximation: positions are TF-IDF keyword vectors reduced to 3D with PCA, computed offline. Real Gemini embeddings group chunks by meaning rather than shared words, so their layout would differ.

3D needs WebGL, which this browser doesn't support. The steps below describe each stage of the animation.

Drag to orbit · scroll to zoom · hover to read

  1. Chunks of text

    All 21 chunks from the 10 lessons, coloured by source lesson. Hover any card to read it.

  2. Text becomes numbers

    Each chunk is turned into a long vector of numbers. The bars show each chunk's strongest dimensions; a real embedding model like gemini-embedding-001 outputs thousands.

  3. Numbers become a position

    Reduced to three dimensions, each vector becomes a point in space. Drag to orbit and scroll to zoom.

  4. Similar topics land close together

    Chunks about related ideas sit near each other. This is what lets a question find relevant text even when the wording differs.

  5. Nearest neighbours

    For one chunk, these are its three most similar chunks by cosine similarity: the same measure used to rank search results.

  6. The index: links between neighbours

    Vector databases connect each point to its neighbours. A search hops along these links toward the target (the yellow path) instead of comparing against every stored vector. That's the idea behind HNSW.

  7. Stored with metadata

    Each point is saved with its text and filename in a Chroma collection on disk. Next: asking a question.

Where this happens in the code

  • src/pipeline/ingest.py: embeds every chunk and writes it to Chroma with its metadata
  • src/pipeline/vector_retrieval.py: reopens the store and searches it
