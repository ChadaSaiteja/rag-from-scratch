1RAG has two halves

Indexing runs once: documents are prepared and stored. Answering runs for every question: find the right pieces, hand them to the model, check the result.

Why it mattersKeeping the two apart is what makes RAG cheap to update (add a document, re-index only that) and easy to debug (which half failed?).

Indexing · once

2Start with documents

This pipeline's knowledge base is 10 short lesson files about RAG itself, in data/raw/.

Why it mattersEverything the system will ever answer comes from here. If a fact isn't in these files, the right answer is “I don't know”.

In this repodata/raw/*.txt · 10 files

Indexing · once

3Load and tag each file

Each file is read into memory and tagged with metadata: its filename. Nothing else changes yet.

Why it mattersThe tag travels with every piece of the document from here on. It is what lets the final answer say which file a fact came from.

In this repoingest.py · ingest()

Indexing · once

4Cut into chunks

Each document is split into pieces of about 1,000 characters, cutting at paragraph breaks where possible. 200 characters are repeated between neighbours (amber) so no sentence is lost at a cut.

Why it mattersA model can only read so much at once, and search works best on focused pieces. Chunk size is the single biggest lever on answer quality.

In this repoingest.py · RecursiveCharacterTextSplitter · 10 files → 21 chunks

Indexing · once

5Turn each chunk into numbers

An embedding model converts each chunk into a long list of numbers (a vector). Chunks with similar meaning get similar numbers.

Why it mattersNumbers can be compared mathematically; words can't. This is what lets a question find a chunk that says the same thing in different words.

In this repoingest.py · gemini-embedding-001 (shown here: a keyword stand-in)

Indexing · once

6Store the vectors

Every vector is saved in a vector database together with its text and its filename tag. Nearby vectors are chunks about similar things.

Why it mattersIndexing is done. From now on the documents are never read again; every question is answered from this store.

In this repoingest.py · Chroma, collection gemini_collection · 21 vectors

Answering · every question

7A question arrives

A user asks something. The system has no idea yet which of the 21 chunks matter.

Why it mattersEverything that follows happens live, in well under a second for a store this size.

In this repogeneration.py · input()

Answering · every question

8Embed the question the same way

The question goes through the same embedding model and lands in the same space as the chunks (the white dot).

Why it mattersSame model, same space: that's the rule. Embed documents and questions differently and nothing is comparable.

In this repohybrid_search.py · GoogleGenerativeAIEmbeddings

Answering · every question

9Vector search: find the nearest meanings

The 3 chunks closest to the question are picked by cosine similarity (how aligned two vectors are).

Why it mattersThis catches chunks that answer the question in different words, which keyword search would miss.

In this repohybrid_search.py · vector_store.as_retriever(k=3) + MultiQueryRetriever

Answering · every question

10Keyword search: find exact words

Independently, BM25 ranks chunks by the exact words they share with the question, weighting rare words more. Its top 3 get amber rings.

Why it mattersVectors blur exact terms like error codes, names and IDs. Keywords catch them. Each method covers the other's blind spot.

In this repohybrid_search.py · BM25Retriever(k=3)

Answering · every question

11Merge the two rankings

Reciprocal Rank Fusion combines both lists by rank, not by score: each chunk scores 0.5 ÷ (60 + rank) per list, summed.

Why it mattersThe two methods score on different scales, so ranks are the only fair thing to add. Chunks both methods like rise to the top.

In this repohybrid_search.py · EnsembleRetriever(weights=[0.5, 0.5])

Answering · every question

12Build the prompt

The winning chunks are pasted under a fixed instruction, each tagged [Source: filename], followed by the question. This exact text is sent to the model.

Why it mattersThe model is told to use only this context, cite the file after every claim, and say “I don't know” otherwise. That instruction is the main defence against made-up answers.

In this repogeneration.py · format_context() + call_google_api()

Answering · every question

13Generate a cited answer

The language model (Gemini) writes the answer from the context, citing the file each claim came from.

Why it mattersBecause the citation points at a real chunk, anyone can check the answer against the source.

In this repogeneration.py · gemini-3.5-flash

Answering · every question

14Check both halves separately

For 5 test questions the pipeline checks two things: did retrieval find the expected file, and does the answer contain the expected idea?

Why it mattersIf an answer is wrong, this tells you which half to fix: the search or the writing. Judging only the final answer can't.

In this repoevaluation.py · retrieval 5/5 · generation 5/5 (as recorded in the README)

15That's the whole pipeline

Documents in, cited answers out, with a check at the end. Every number you saw came from this repository's real corpus and settings.

Why it mattersNow try it with your own question, or read the code that does each step.

What is real: the files, the 21 chunks and split points, the question, the BM25 scores, the rank fusion, the prompt text and the recorded answer and scores. What is a stand-in: vector positions use TF-IDF keyword vectors reduced to 3D (computed offline, no API key) instead of Gemini embeddings, so the layout of the point cloud would differ with real embeddings.
